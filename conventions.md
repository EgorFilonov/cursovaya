# Правила работы над проектом

Соглашения, по которым ведётся эта курсовая. Документ нужен автору и может быть показан как пример того, как в проекте договариваются о стиле и процессе.

Проект на Python. Правила кода — PEP 8 и Ruff, параметр `self`, docstring.

Issue с этими правилами не закрывается: его дополняют по ходу разработки. Закрывающие формулировки (`Fixes`, `Closes`, `Resolves`) в pull request для этого issue не используются.

## 1. Стиль именования

Имена соответствуют [PEP 8](https://peps.python.org/pep-0008/). Проверка — Ruff.

| Элемент | Стиль | Пример |
| --- | --- | --- |
| Модуль и пакет | snake_case, короткое имя | `service_requests` |
| Класс, исключение, перечисление | PascalCase | `ServiceRequest` |
| Функция и метод | snake_case | `change_status` |
| Переменная, параметр, атрибут | snake_case | `request_id` |
| Непубличный атрибут | один префикс `_` | `_requests` |
| Константа уровня модуля | UPPER_CASE | `MAX_TITLE_LENGTH` |
| Первый параметр метода экземпляра | `self` | `def save(self)` |
| Первый параметр метода класса | `cls` | `def create(cls)` |

Дополнительно:

- Аббревиатуры пишутся как обычные слова: `request_id`, `api_url`, а не `request_ID`.
- Логические имена начинаются с `is_`, `has_` или `can_`: `is_closed`.
- Венгерская нотация не используется.
- Однобуквенные имена допустимы только у счётчиков циклов (`i`, `j`).
- Идентификаторы в коде — на английском. Тексты предметной области для пользователя и документация — на русском.
- Импорты: стандартная библиотека, затем сторонние пакеты, затем модули проекта. Каждую группу отделяет пустая строка.

## 2. Параметр `self`

У метода экземпляра первый параметр всегда называется `self`. Через него идёт обращение к атрибутам и другим методам.

`self` не опускается и не переименовывается. Локальная переменная не должна называться `self`.

```python
class RequestService:
    def __init__(self, repository: RequestRepository) -> None:
        self._repository = repository

    def rename(self, request_id: int, title: str) -> None:
        self._repository.update_title(request_id, title)
```

Если параметр метода совпадает по смыслу с атрибутом, атрибут всё равно читается через `self`, а параметру дают обычное имя.

## 3. Документирование

У публичных модулей, классов и функций есть docstring. Формат — [Google style](https://google.github.io/styleguide/pyguide.html#38-comments-and-docstrings): его понимает Sphinx через Napoleon.

Обязательные части:

- первая строка — что делает объект, в повелительном наклонении;
- `Args` — у каждого параметра, кроме `self` и `cls`;
- `Returns` — если функция что-то возвращает;
- `Raises` — если вызывающий код должен обработать исключение.

По смыслу добавляются `Attributes` и пример в секции `Examples`.

Пустой docstring и фраза, которая только повторяет имя функции, не допускаются. Комментарий `#` объясняет неочевидное решение, а не пересказывает следующую строку.

```python
def change_status(request_id: int, status: RequestStatus) -> ServiceRequest:
    """Меняет статус заявки.

    Args:
        request_id: Идентификатор заявки.
        status: Новый статус.

    Returns:
        Заявка с уже записанным статусом.

    Raises:
        KeyError: Заявки с таким идентификатором нет.
    """
```

У эндпоинтов FastAPI краткое описание из docstring попадает в OpenAPI и отображается в Swagger UI. Публичный контракт меняется вместе с docstring, иначе страница `/docs` разойдётся с кодом.

## 4. Сообщения коммитов

Формат — [Conventional Commits](https://www.conventionalcommits.org/):

```text
<тип>: <краткое описание>
```

Описание — на русском, в повелительном наклонении, без точки в конце. Один коммит — одно логическое изменение.

| Тип | Когда |
| --- | --- |
| `feat` | новая возможность |
| `fix` | исправление ошибки |
| `docs` | только документация |
| `style` | оформление без изменения поведения |
| `refactor` | перестройка кода без новой возможности и без исправления ошибки |
| `test` | тесты |
| `chore` | служебные файлы, шаблоны, настройки |
| `ci` | конвейер сборки |
| `build` | зависимости и скрипты сборки |

Примеры:

```text
feat: добавить смену статуса заявки
docs: сопоставить документы ГОСТ с современными аналогами
ci: добавить pytest в GitHub Actions
```

Тело коммита нужно, только если из заголовка неясно, зачем сделано изменение.

## 5. Ветки и pull request

- Основная ветка — `master`. После начального коммита со структурой репозитория прямой push в `master` не делается.
- Каждая задача начинается с issue.
- Ветка создаётся от `master` и называется `feature/<номер issue>`.
- Результат сдаётся pull request в `master`.
- Ревьюер — [MarinaPaley](https://github.com/MarinaPaley).
- В описании PR есть ссылка на issue (`#123`). Для issue с правилами работы нельзя употреблять слова, которые GitHub считает закрывающими.
- Одна задача — один pull request.
- Перед открытием PR локально проходят `ruff check .` и `pytest`.

## 6. Прочие договорённости

- Файлы документации репозитория (`README`, эти правила и другие пояснения к проекту) — только Markdown.
- Текст, который войдёт в пояснительную записку, ведётся в MS Word. Такие файлы лежат в папке `КР/`, отдельно от кода.
- `.docx` и другие бинарные форматы помечены в `.gitattributes`, чтобы Git не пытался слить их как текст.
- Секреты, пароли и строки подключения в репозиторий не попадают. Виртуальное окружение `.venv` и кэш `__pycache__` туда тоже не попадают.
- Зависимости фиксируются в `requirements.txt`.
- Аннотации типов ставятся на публичные функции.
- Сборка и тесты на сервере выполняет GitHub Actions: Python 3.12, Ruff и pytest.

## 7. Как дополнять правила

Новый пункт добавляется в этот файл отдельным коммитом и коротко поясняется комментарием в issue «Правила работы над проектом». Само issue остаётся открытым.
