# Правила работы над проектом

Соглашения, по которым ведётся эта курсовая. Документ нужен автору и может быть показан как пример того, как в проекте договариваются о стиле и процессе.

Issue с этими правилами не закрывается: его дополняют по ходу разработки. Закрывающие формулировки (`Fixes`, `Closes`, `Resolves`) в pull request для этого issue не используются.

## 1. Стиль именования

Имена соответствуют [соглашениям C#](https://learn.microsoft.com/dotnet/csharp/fundamentals/coding-style/coding-conventions) и правилам StyleCop.Analyzers.

| Элемент | Стиль | Пример |
| --- | --- | --- |
| Пространство имён | PascalCase, совпадает с папками | `ServiceRequests.Api.Controllers` |
| Класс, структура, record, enum | PascalCase | `ServiceRequest` |
| Интерфейс | `I` + PascalCase | `IRequestRepository` |
| Метод, свойство, событие | PascalCase | `ChangeStatus` |
| Асинхронный метод | PascalCase + суффикс `Async` | `GetByIdAsync` |
| Параметр и локальная переменная | camelCase | `requestId` |
| Приватное и внутреннее поле | `_` + camelCase | `_repository` |
| Константа и член enum | PascalCase | `MaxTitleLength` |
| Параметр типа | `T` + PascalCase | `TResult` |
| Файл | имя основного типа | `ServiceRequest.cs` |

Дополнительно:

- Аббревиатуры пишутся как обычные слова: `Id`, `Api`, `Url`, а не `ID` и `URL`.
- Логические имена начинаются с `is`, `has` или `can`: `isClosed`.
- Венгерская нотация не используется.
- Однобуквенные имена допустимы только у счётчиков циклов (`i`, `j`).
- Идентификаторы в коде — на английском. Тексты предметной области для пользователя и документация — на русском.

## 2. Ключевое слово `this`

Поля именуются с префиксом `_`, поэтому член класса и параметр не совпадают по написанию. Обращение к полю, свойству и методу пишется без `this`.

`this` ставится только чтобы снять неоднозначность, если параметр или локальная переменная скрывает член класса:

```csharp
public sealed class RequestService
{
    private readonly IRequestRepository _repository;

    public RequestService(IRequestRepository repository)
    {
        _repository = repository;
    }
}
```

Правило StyleCop SA1101 (обязательный префикс `this.`) в проекте не включается: оно расходится с соглашениями Microsoft для полей с префиксом `_`. Настройка зафиксирована в `.editorconfig` (`dotnet_style_qualification_for_field`, `dotnet_style_qualification_for_property` и `dotnet_style_qualification_for_method` равны `false`).

## 3. XML-документация

У каждого публичного типа и публичного члена есть комментарий `///`.

Обязательные теги:

- `summary` — что делает тип или член;
- `param` — у каждого параметра;
- `returns` — если метод возвращает значение;
- `exception` — если метод выбрасывает исключение, на которое рассчитывает вызывающий код.

По смыслу добавляются `remarks`, `example`, `see`, `seealso`, `paramref`, `typeparam`, `inheritdoc`.

Пустой `summary` и комментарий, который только повторяет имя метода, не допускаются.

Doxygen разбирает XML-комментарии C#. В проекте используются теги, которые Doxygen понимает без отдельного синтаксиса `\brief`:

| Тег C# | Роль для Doxygen |
| --- | --- |
| `summary` | краткое описание, аналог `\brief` |
| `remarks` | подробности, аналог `\details` |
| `param` | параметр |
| `returns` | возвращаемое значение |
| `exception` | исключение |
| `example` | пример |
| `see`, `seealso` | перекрёстная ссылка |

Генерируемый XML-файл документации включается свойством `GenerateDocumentationFile`. Предупреждение CS1591 для публичных API не подавляется: отсутствие комментария должно быть видно при сборке.

## 4. Сообщения коммитов

Формат — [Conventional Commits](https://www.conventionalcommits.org/):

```text
<тип>: <краткое описание>
```

Описание — на русском, в повелительном наклонении, без точки в конце. Один коммит — одно логическое изменение.

| Тип | Когда |
| --- | --- |
| `feat` | новая возможность |
| `fix` | исправление ошибки |
| `docs` | только документация |
| `style` | оформление без изменения поведения |
| `refactor` | перестройка кода без новой возможности и без исправления ошибки |
| `test` | тесты |
| `chore` | служебные файлы, шаблоны, настройки |
| `ci` | конвейер сборки |
| `build` | зависимости и скрипты сборки |

Примеры:

```text
feat: добавить смену статуса заявки
docs: сопоставить документы ГОСТ с современными аналогами
ci: добавить сборку и тесты в GitHub Actions
```

Тело коммита нужно, только если из заголовка неясно, зачем сделано изменение.

## 5. Ветки и pull request

- Основная ветка — `master`. После начального коммита со структурой репозитория прямой push в `master` не делается.
- Каждая задача начинается с issue.
- Ветка создаётся от `master` и называется `feature/<номер issue>`.
- Результат сдаётся pull request в `master`.
- Ревьюер — [MarinaPaley](https://github.com/MarinaPaley).
- В описании PR есть ссылка на issue (`#123`). Для issue с правилами работы нельзя употреблять слова, которые GitHub считает закрывающими.
- Одна задача — один pull request.
- Перед открытием PR локально проходят `dotnet build` и `dotnet test`.

## 6. Прочие договорённости

- Файлы документации репозитория (`README`, эти правила и другие пояснения к проекту) — только Markdown.
- Текст, который войдёт в пояснительную записку, ведётся в MS Word. Такие файлы лежат в папке `КР/`, отдельно от кода.
- `.docx` и другие бинарные форматы помечены в `.gitattributes`, чтобы Git не пытался слить их как текст.
- Секреты, пароли и строки подключения в репозиторий не попадают.
- Публичный контракт контроллера меняется вместе с XML-комментарием, чтобы описание в Swagger оставалось точным.
- Сборка и тесты на сервере выполняет GitHub Actions (`.github/workflows/dotnet.yml`): .NET 10, конфигурация Release, NUnit.

## 7. Как дополнять правила

Новый пункт добавляется в этот файл отдельным коммитом и коротко поясняется комментарием в issue «Правила работы над проектом». Само issue остаётся открытым.
